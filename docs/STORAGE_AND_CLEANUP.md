# Хранение данных и очистка мусора (price-radar)

## Где хранится история проверок цен

История цен хранится в JSON-файлах формата:

```json
{
  "<ключ-товара>": [
    { "t": 1794063332853, "p": 299118 },
    { "t": 1794157062942, "p": 290144, "m": 1 }
  ]
}
```

- `t` — время проверки (unix ms), `p` — цена, `m` — признак ручной/особой точки (если используется).
- **GitHub Actions (серверная проверка, `scripts/check-prices.mjs`)**: читает и коммитит `public/data/history.json`, `public/data/products.json`, `public/data/push-subscriptions.json` в репозиторий. Эти данные использует PWA на GitHub Pages.
- **Локальный агент (`scripts/check-prices-local.mjs`)**: работает с локальными данными (в т.ч. `data/`), в зависимости от режима — см. скрипт.
- **Ограничение по времени:** в `scripts/check-prices.mjs` задано `MAX_AGE = 180 дней` — при обновлении старые точки (старше 180 дней) отрезаются, то есть рабочая история **не растёт бесконечно по времени**.
- **Ограничение по частоте записей:** новая точка добавляется, если цена изменилась или с последней точки прошло > 24 часов. При стабильной цене это ~1 точка/сутки на товар.

### Оценка объёма при 100+ товарах

Грубая оценка для рабочего файла `public/data/history.json`:

- 1 точка ≈ 30–50 байт в JSON.
- Верхняя граница: 100 товаров × 180 точек (1/день) × 50 байт ≈ **~0.9 MB**.
- 500 товаров × 180 точек × 50 байт ≈ **~4.5 MB**.
- Реально часто меньше (запись не на каждый прогон, если цена не менялась и прошло < 24 ч).

**Где это занимает место:**
- В **git-репозитории и на GitHub** — `public/data/history.json` попадает в коммиты workflow проверки цен. Размер *рабочего* файла ограничен ~180 днями, но git хранит прошлые версии в истории/объектах.
- На **диске ПК** — рабочая копия + `.git` (объекты/pack).
- На **GitHub Pages** — деплоится актуальная статика/`out/` с текущим `public/data/history.json` (не вся git-история).

Если рост станет проблемой: можно уменьшить `MAX_AGE`, писать только при изменении цены, хранить агрегаты или вынести историю из git во внешнее хранилище — это архитектурное изменение.

## Локальный мусор на ПК (обычно gitignored)

| Что | Где | Можно ли чистить |
|---|---|---|
| Логи watcher/check-prices | `logs/*.log` | Да, старые/большие (см. скрипт) |
| Состояние watcher | `.local/opencode-issues.json`, lock | **Не удалять** без необходимости (дедупликация/статусы задач) |
| Профиль браузера агента | `.local/edge-profile/**` | Осторожно: cookies/сессии нужны для локальных проверок. Безопасно чистить `BrowserMetrics/*.pma`, crash reports, cache-папки (пересоздаются) |
| Артефакты сборки | `.next/`, `out/`, `tsconfig.tsbuildinfo` | Да, пересобираются (`npm run build`/`dev`) |
| Зависимости | `node_modules/` | Да, восстанавливаются (`npm ci`/`npm i`) |

## Скрипт очистки

Сухой прогон (ничего не удаляет, показывает объём):

```bash
node scripts/cleanup.mjs
```

Фактическая очистка:

```bash
node scripts/cleanup.mjs --apply
node scripts/cleanup.mjs --apply --logs-days 14 --keep-issue-logs 20 --max-main-log-mb 5
```

Скрипт не трогает исходники, `.env`, `data/products.json`, `public/data/*`, git-историю и `.local/opencode-issues.json`.

## GitHub: issues, задачи, «версии»

- **Issues**: промежуточные/закрытые задачи стоит держать закрытыми с комментарием-итогом (watcher закрывает успешные автоматически). Массовое удаление issues через git недоступно — только вручную/через API администратором.
- **Workflow runs / артефакты Actions**: старые runs занимают место в интерфейсе; retention/очистку можно настроить в Settings → Actions или удалять вручную.
- **Releases/tags**: промежуточные релизы/теги, если появятся, удаляются вручную в GitHub Releases/Tags.
- **Ветки/tags git**: чистятся стандартными командами при необходимости, осознанно.
